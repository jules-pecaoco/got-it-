# Security model and limitations

Server-side evaluation reads private rules from SQLite and writes immutable score events under `(session_id, activity_id, criterion_id)` primary keys. A transaction records each submission and inserts score events with `INSERT OR IGNORE`; retries cannot increase an already awarded criterion. A stable `Idempotency-Key` plus a request hash makes transport retries return the original attempt without charging another retry. Candidate drafts are stored separately and become final submissions on finish or expiry, subject to retry limits. Candidate endpoints return public prompts, drafts for the current candidate, and progress. Practice runs also return immediate correctness and score; Graded runs withhold both until faculty publishes the completed attempt's score. Extending or reopening an attempt clears early publication, and active Graded attempts remain hidden before run close. Existing runs retain their stored feedback mode. Published exam versions are immutable, and sessions remain pinned to their run's version.

The server uses opaque tokens and does not trust browser-supplied score, deadline, order, role or answer keys. Browser clients use role/path/tab-scoped HttpOnly, SameSite=Strict cookies; tokens are omitted from browser sign-in JSON and are not stored in Web Storage. HTTPS deployments set `PUBLIC_ORIGIN` so cookies are Secure behind a TLS proxy and Origin checks use the public origin. Cross-origin mutations are rejected. Scripted clients retain bearer authentication. Faculty access expires after eight hours, candidate access after 24 hours, and logout revokes the server token. Student logout or token expiry preserves the attempt for rejoin, including its original deadline. Legacy tokens without expiry require one rejoin on upgrade. Run PINs stay in the current Faculty page's memory until refresh or logout; legacy browser credentials are purged on page load.

Admission checks roster identity, PIN, and window. Scoring also checks mission unlock and the server deadline. Answer checks are limited to six per minute per session and activity. Student readiness/join has a 5,000-request/minute socket-IP ceiling, plus separate failed-credential limits of ten per run/candidate and 200 per socket IP per minute. Successful requests do not consume failed-credential budgets. Forwarded client-address headers are not trusted. Rate-limit memory is bounded and expired entries are removed. Static serving is confined to `public/`. JSON bodies enforce byte limits and reject malformed UTF-8; mission and question IDs must match the API's addressable format before publication. Errors include a request ID. CSV export escapes formula-leading cells.

Faculty-only review endpoints expose submitted answers, answer keys, and per-question scores. Score overrides and recovery actions are recorded with a reason in the audit log. Recovery is limited to 1–120 minutes and is available before the run closes; time extension applies to an active or expired attempt, while reopening applies to a submitted or expired attempt. Candidate and Proctor endpoints do not expose faculty review or recovery controls. Proctor access is separate from student and faculty access. Faculty chooses a run-specific code of 8–100 characters, stored only as a hash. Proctor tokens are limited to that run and expire when it closes or after eight hours. Replacing or revoking the code deletes existing proctor tokens. The monitoring response includes names, school IDs, participation and submission timing, but no responses, scores, private rules, or answer keys. Proctors share a run code rather than signing in as individually identified staff; the code should only be given to authorized facilitators.

**Supervised identity model:** school ID plus a shared run PIN remains intentional because each activity is proctored. Anyone who knows both can join that school ID's attempt; proctors are responsible for checking the student's identity. Faculty accounts scope ownership; legacy records belong to the initial `faculty` account. The run PIN uses unsalted SHA-256. Demo mode has a known fallback faculty password; disable it and set a password for deployment. TLS termination, secure secret management, backup/restore operations, data retention, comprehensive denial-of-service controls, multi-process concurrency review, accessibility testing and penetration testing remain deployment responsibilities. Node's built-in SQLite API is experimental in the tested runtime.

The source files in `examples/` include fictional private answers so developers can inspect and test the package contract. They are outside `public/` and are not served by the app. Do not place a real exam answer file in a public checkout or client bundle. Use a protected deployment store and access controls for real content.

Before real graded deployment: complete a roster/authentication audit, faculty question and rubric review, end-to-end security review, concurrency/load test, representative full-duration pilot, incident recovery drill, and data governance review. Student fullscreen and disabled text selection are light deterrents. Browser fullscreen can be exited, and screenshots or photographs cannot be reliably blocked by this web app. There are no focus strikes or automatic penalties.

## Coding execution

`code_writing` never evaluates student source in the application process, browser, or host interpreter. Each test starts a fresh digest-pinned Docker Linux container with no network, host mounts, privileged capabilities, or application environment. It runs as UID/GID 65534, with a read-only root, a 16 MB noexec/nosuid/nodev tmpfs, 128 MB memory, 32 PIDs and 0.5 CPU. The host bounds execution to six seconds and combined output to 32 KB; runtime wrappers add program timeouts where available. Containers are force-removed on success, failure, output limit and timeout. Two simultaneous containers are allowed. SQL creates a fresh in-memory SQLite database, disables extension loading and authorizes read-only query operations after fixture setup.

Only the student's source and one test input enter a container; expected outputs, reference solutions, student records, application secrets and Docker socket paths do not. Comparison and point awards stay in the server. Public sample execution never runs hidden inputs. Submitted output and claimed success flags are ignored. Private-test runtime diagnostics are withheld from student responses. Missing images, daemon outages, or capacity errors fail without recording an attempt. Server status/deadline and retry allowance are checked again before recording an asynchronous execution result. Docker is a container boundary, not a complete hostile multi-tenant sandbox: use a dedicated worker host and hardened/rootless runtime for public or adversarial deployments. See [Docker security](https://docs.docker.com/engine/security/) and [container controls](https://docs.docker.com/engine/containers/run/).
