# Security model and limitations

Server-side evaluation reads private rules from SQLite and writes immutable score events under `(session_id, activity_id, criterion_id)` primary keys. A transaction records each submission and inserts score events with `INSERT OR IGNORE`; retries cannot increase an already awarded criterion. A stable `Idempotency-Key` plus a request hash makes transport retries return the original attempt without charging another retry. Candidate answer drafts are stored separately from submissions and are not graded or scored. Candidate endpoints return public prompts, drafts for the current candidate, and progress. Practice runs also return immediate correctness and score; Graded runs withhold both until the run closes. Existing runs retain Practice feedback. Published exam versions are immutable, and sessions remain pinned to their run's version.

The server uses opaque bearer tokens and does not trust browser-supplied score, deadline, order, role or answer keys. It checks roster identity, PIN, window, mission unlock and deadline before a score mutation. Answer checks are limited to six per minute per session and activity; join and instructor login have IP limits. Static serving is confined to `public/`. Errors include a request ID. CSV export escapes formula-leading cells.

Faculty-only review endpoints expose submitted answers, answer keys, and per-question scores. Score overrides and recovery actions are recorded with a reason in the audit log. Recovery is limited to 1–120 minutes and is available before the run closes; time extension applies to an active or expired attempt, while reopening applies to a submitted or expired attempt. Candidate and Proctor endpoints do not expose faculty review or recovery controls. Proctor access is separate from student and faculty access. Faculty issues a random run-specific code, stored only as a hash. Proctor tokens are limited to that run and expire when it closes or after eight hours. Replacing or revoking the code deletes existing proctor tokens. The monitoring response includes names, school IDs, participation and submission timing, but no responses, scores, private rules, or answer keys. Proctors share a run code rather than signing in as individually identified staff; the code should only be given to authorized facilitators.

**Not production ready:** the shared PIN and school ID are suitable only for the supervised isolated lab described by the instructor; someone who knows both can join another student's attempt. Demo access details are intentionally displayed. The PIN uses unsalted SHA-256. Bearer tokens live in browser session storage. TLS termination, secure secret management, backups, data retention, CSRF/CORS review, denial-of-service controls, multi-process concurrency review, accessibility testing and penetration testing are not provided. Node's built-in SQLite API is experimental in the tested runtime.

The source files in `examples/` include fictional private answers so developers can inspect and test the package contract. They are outside `public/` and are not served by the app. Do not place a real exam answer file in a public checkout or client bundle. Use a protected deployment store and access controls for real content.

Before real graded deployment: complete a roster/authentication audit, faculty question and rubric review, end-to-end security review, concurrency/load test, representative full-duration pilot, incident recovery drill, and data governance review. Student fullscreen and disabled text selection are light deterrents. Browser fullscreen can be exited, and screenshots or photographs cannot be reliably blocked by this web app. There are no focus strikes or automatic penalties.
